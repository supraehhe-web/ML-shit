# Paper reproduction: the released DM-AHR checkpoint on its own data

Generated by `scripts/25_build_diagnosis_reports.py` from `artifacts/logs/paper_reproduction*.json`, `dermahair_sample_audit.json`. Reference: the DM-AHR paper, *Cancers* 2024, 16, 2947, as supplied by the project owner (not re-fetched here).

## Outcome

- **Pre-registered rule (decision log D22), 128 px, 2,000 steps:** mean PSNR must be at least 39.04 dB (within 2 dB of 41.04). Measured **34.92 dB**, so the rule is **not met**: *paper numbers not reproduced* at 128 px.
- **Native-resolution diagnostic (run only because the 128 px rule failed):** at 256 px, the size of the DERMAHAIR files, PSNR is **41.15 dB**, SSIM **0.966** (paper: 41.04 dB, 0.966). That is within 0.11 dB of the paper, on 40 pairs of a single-class sample. The adapter and checkpoint loading reproduce the paper once the checkpoint is run at the resolution of its data.
- **What that means for this study:** the adapter's `native_resolution` of 128 px (taken from the upstream config's `r_resolution`) is not the resolution the released weights operate at; the upstream data loader (`data/LRHR_dataset.py`) performs no resizing, and the files are 256 x 256. Anything that ran the *released* weights at 128 px (the D19 head-to-head, and any arm built on them) used them off their native scale.
- **What this does not show:** the 256 px run used the 101-pair akiec subset vendored in the upstream repository (one of seven classes, 40 pairs scored at 256 px), not the 700-image DERMAHAIR test set. The Kaggle dataset could not be downloaded (no Kaggle credentials in this environment). The paper's own hairy-input floor is not reported, so the paper's number cannot be placed against a no-model baseline.

## What was run

- Checkpoint `I725000_E1083_gen.pth` loaded strictly through `dm_ahr_vit.diffusion.dmahr_adapter.load_model`; upstream sampler (`super_resolution`), bf16 autocast = True.
- Source: vendored DERMAHAIR akiec subset only (101 pairs; partial: one class).
- 128 px: 101 pairs scored, 50 identity round-trips; steps 2,000 and 1,000. 256 px: 40 pairs, 20 identity round-trips; 2,000 steps.
- Three conditions per setting: **floor** (hairy input against the hairless reference, no model), **identity** (the hairless reference pushed through the full inference path and compared with itself), **output** (hairy input through the model against the reference). The hairless references may contain natural hair; they were not filtered.
- LPIPS uses AlexNet (`lpips` 0.1.4) on [-1, 1] inputs; the paper's LPIPS network and scaling are not stated here, so LPIPS is reported but not used in any rule.

## Released-config audit

- The seven class configs resume from the same checkpoint name (`I725000_E1083`): single shared checkpoint = True. Their `model` and `train` blocks are identical = True; only `dataroot` differs. **`akiec.json` does not imply a class-specific checkpoint**; it selects the evaluation folder.
- Training-data path in `akiec.json`: `hair_removal/akiec_16_128` (the class-specific `*_16_128` folder). The configs do not document what data the released weights were trained on; the paper, as supplied, states HAM10000 images outside the 700-image test set were used for training, so the released weights have very likely seen this study's validation and test clean images.
- Iterations: config `n_iter` = 660,000; released checkpoint is iteration 725,000 (more than `n_iter` = True); the paper's stated count is 20,000. The paper's text contradicts its own release.
- Batch size 4, lr 0.0001, gradient clipping in the upstream trainer = False.

## Conclusion

1. The released checkpoint, run through this adapter at 256 px with 2,000 steps, reproduces the paper's PSNR and SSIM on the vendored single-class sample. The adapter, strict weight loading and value range are therefore sound *at the checkpoint's own resolution*.
2. At the 128 px this repository assumed, the same weights score about 6 dB lower, so the pre-registered rule (128 px) is reported as not met. Anything that evaluates the released weights at 128 px (including the D19 head-to-head) used them off their native scale.
3. This says nothing about Arm C directly: Arm C used a checkpoint trained here at 128 px, and its failure is explained in `reports/arm_c_diagnosis_v2.md`.
